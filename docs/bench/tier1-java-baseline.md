# Java Tier-1 baseline -- snapshot

Generated 2026-05-16, workspace at `469d345` (weld 0.19.1).

This document is the frozen reference for the post-promotion Java
Tier-1 state. It records the per-criterion outcome of
`tools/tier_check.py` against each of the five pinned corpora
declared in [`tier1-corpora.yaml`](tier1-corpora.yaml). It is
intentionally diff-friendly: a future regression to any of the
structural facts below (kind correctness, edge counts, F1 scores,
determinism SHA-256, performance LOC, framework strategies) will show
as a line-level change in this file.

The numbers were generated by running `python3 -m weld discover`
against each pinned corpus at workspace HEAD, followed by
`python3 tools/tier_check.py --language java --corpus <corpus>
--rediscover --json`. See "How to refresh" at the bottom.

`//tools:tier_check_java_gate_test`. That gate is the

## Snapshot data (kind=None and the criterion-6 stub)

Every Java symbol node in every corpus carries `kind=None` from the
java tree-sitter strategy
(`weld/strategies/_java_tree_sitter.py`). The criterion-1 contract
explicitly accepts `None` as a valid kind value (it is not a
mis-pluralised or otherwise mangled vocabulary token), which is why
C1 reports `pass` with `bad_count=0` and a vocabulary of
`{class, enum, interface, method, record}` (the canonical vocabulary
declared in `tools/tier_check_kinds`, not the per-corpus emitted
set).

A direct consequence is that criterion 6 (description coverage)
cannot find any "meaningful" symbol: its filter scans for symbols
whose `kind` is in `{class, enum, function, interface, method}`,
and every Java symbol has `kind=None`. The criterion module
therefore returns `status='stub'` with the documented
"no meaningful symbols observed" reason. Criterion 6 is advisory
under the criterion-6 amendment so this does not block Tier-1
promotion. Backfilling the Java strategy to emit a concrete kind
(`class` / `interface` / `method`) on each symbol is a continuous
improvement task and would flip C6 from stub to a measurable
(pass/fail) percentage; it does not change the Tier-1 verdict
today.

- C8 `fail` is fixture-noise: a 70-100 LOC sample inflates

  startup cost over too little code. Tier-1 promotion measures
  C8 against the pinned external corpora, not bundled fixtures.

## How to refresh

The doc above is reproducible from the workspace HEAD plus the five
pinned corpora. To regenerate:

```bash
# 1. Materialise the corpora at their pinned SHAs (idempotent).
python3 tools/tier1_corpus.py --language java --fetch \
    --output /tmp/weld-tier1-corpora-java

# 2. Re-run tier_check against each. --rediscover ensures the corpus
#    graph is built with workspace-HEAD weld (not a possibly-lagging
#    installed wd binary). --json captures the full criterion payload.
for corpus in guava spring-boot junit5 gson commons-lang; do
    PYTHONPATH=. python3 tools/tier_check.py \
        --language java \
        --corpus /tmp/weld-tier1-corpora-java/$corpus \
        --rediscover \
        --json > /tmp/tc-java-$corpus.json
done

# 3. Inspect verdicts and per-criterion status.
for f in /tmp/tc-java-*.json; do
    python3 -c "import json,sys; d=json.load(open(sys.argv[1])); \
        print(d['corpus'], '->', d['verdict']); \
        [print(' ',k,v['status']) for k,v in sorted(d['criteria'].items())]" \
        "$f"
done
```

Workspace SHA, corpus SHAs, kind vocabulary, edge counts, F1
scores, determinism SHA-256s and LOC counts are deterministic and
should reproduce byte-identically. The `wall_clock` values in the
performance criterion are wall time and will vary by host -- the
`seconds_per_100k_loc` column is bound by the 60 s/100k-LOC budget
declared in ADR 0064 and is the field that matters for regression
detection.

If any structural fact above changes against the same workspace SHA
and corpus SHA pair, that is a real regression and should be filed
as a bd issue against the Java Tier-1 epic.
